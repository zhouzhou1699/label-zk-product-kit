# 数据模型与状态机

> 全部字段名与取值来自真实接口响应（`07-data/samples/`），非推测。脱敏处已标注 `REDACTED`。

## 一、实体关系总图

```
Institution(单位)  1 ── n Organization(团队)  1 ── n Workspace(空间)  1 ── n Project(项目)
   │                        │                        │                       │
   │                        │                        │                       ├─1─n Task(任务)
   │                        │                        │                       ├─1─n Annotation(标注)
   │                        │                        │                       ├─1─n Prediction(预测)
   │                        │                        │                       ├─1─n ImportBatch(导入批次)
   │                        │                        │                       └─1─n ProjectAssignment(项目角色)
   │                        │                        └─n Membership(空间成员)
   │                        └─n Membership(团队成员) ── User(账号)
   ├─1─1 CloudStorage(OSS 配置)
   ├─1─n ModelConfig(模型凭证)
   ├─1─1 Personalization(品牌/首页装扮)
   ├─1─n DatasetCategory(分类树)
   └─1─n CertificateTemplate(证书模板)

Dataset(数据集)  n ── 1 Institution / Team，可被 n 个 Project 引用（引用不复制）
PointsTransaction(积分流水)  n ── 1 User × Project
Certificate(证书)  n ── 1 User × Project × CertificateTemplate
AuditLog(审计)  n ── 1 Actor × 任意对象
```

## 三、任务状态机（产品内核）

```
                        ┌────────────── 撤回发布（不删标注）──────────────┐
                        │                                             │
  [数据导入] → [生成任务] → 待领取 ──领取──→ 标注中 ──提交──→ 待审核 ──一审通过──→ 待验收
     unclaimed            unclaimed         annotating     pending_review    pending_validation
                              ↑                  ↑                                    │
                              │                  │                              终审通过│
                              │                  │                                    ↓
                              │                  └──────── 已打回 ←── 一审/终审打回 ──┤
                              │                        rejected                     │
                              │                                                    ↓
                              └──────────── 重新提交（reject_count +1）──────────  已通过 passed
                                                                              ★ 积分结算点
                                                                              ★ 证书评估点
                                                                              ★ 验收台账写入
```

### 状态定义表

| 状态 | 中文 | 进入条件 | 可执行动作 | 退出路径 |
|---|---|---|---|---|
| `unclaimed` | 待领取 | 项目已发布 + 任务已生成 | 领取 | → `annotating` |
| `annotating` | 标注中 | 被标注员领取 / 存过草稿 | 更新草稿、提交 | → `pending_review`（提交） |
| `pending_review` | 待审核 | 标注员提交 | 质检员通过/打回 | → `pending_validation` / `rejected` |
| `pending_validation` | 待验收 | 一审通过 | 验收员通过/打回/评分 | → `passed` / `rejected` |
| `passed` | 已通过 | 终审通过 | 导出、进训练集 | 终态（可重置） |
| `rejected` | 已打回 | 一审或终审打回 | 修改后重新提交 | → `annotating`（`reject_count+1`） |

### 状态机的三个产品决策（值得学）

1. **"已提交"仍留在"进行中"**——数据页把已提交任务留在标注员视野里，仅排序靠后。降低"我提交了去哪了"的焦虑。
2. **打回不改状态为"待领取"**，而是进"待处理"，保证**任务归属人不变**——避免好任务被打回后被别人抢走。
3. **撤回发布只暂停新领取**，不改已有任务状态——发布是"阀门"不是"开关"。

### 状态机的两个缺陷

1. **`annotating` 与"已标注"混淆**：勾了「更新」（存草稿）但没点「提交」，任务永久卡在"标注中"，界面上与"正在标"无区别。手册把它列进 FAQ，说明这是高频客诉。**建议**：`annotating` 拆成 `drafting`(有草稿未提交) / `working`(已领取未保存)，并在卡片上给"草稿超 24h"黄标。
2. **打回扣分时机错位**：扣分在"最终通过"时按次数结算，任务若最终未通过则打回零成本 → 激励"先交再改"。**建议**：打回即扣（可回滚），或对 `reject_count ≥ 2` 的任务降低基础分系数。

## 四、发布前检查（四项，实测接口 `workflow/preconditions`）

```json
{"all_ok": true, "workspace": {"id":44,"title":"测试空间"},
 "items":[
   {"key":"label_config","ok":true,"count":1,"link":"/projects/218/settings/labeling"},
   {"key":"data_imported","ok":true,"count":30,"link":"/projects/218/imports"},
   {"key":"in_workspace","ok":true,"name":"测试空间"},
   {"key":"workspace_members","ok":true,"count":1}
 ]}
```

| 检查项 | 通过条件 | 未通过时用户看到的 |
|---|---|---|
| 标签配置 | 至少 1 个业务类别 | "已设置 N 个业务类别" + 快捷跳转 |
| 数据已导入 | 项目内已有数据条目 | "已导入 N 条数据" + 「继续导入」 |
| 任务已生成 | 数据已转成任务 | "已生成 N 个任务，待领取 M 个" |
| 成员与角色 | 空间内有成员 + 三角色已设 | "团队空间 N 名成员 · 标注/审核/验收已设" |

**产品价值**：把"发布失败"从错误弹窗变成**清单式引导**，每项都有出口链接。这是全站最值得复用到其它模块（训练任务、模型部署）的模式。

## 五、积分结算模型

```
points = max(0, base + rating_bonus + first_draft_bonus − reject_penalty × reject_count)
```

| 参数 | 语义 | 结算时机 |
|---|---|---|
| `base` | 每个通过任务必得 | 终审通过 |
| `rating_bonus` | 验收员质量评分 0–100 落档加成 | 终审通过 |
| `first_draft_bonus` | `reject_count == 0` 才发 | 终审通过 |
| `reject_penalty` | 每次打回扣一次（一审/终审各计 1） | 终审通过时一次性扣 |

**不计分的五种情况**（手册明文）：仅提交未通过 / 打回后未再通过 / 实训模式项目 / 被跳过的标注 / 无归属人的任务。

**评分后修改的处理**：只补写一条**差额流水**，不重复发放基础分——账本设计正确（append-only + 差额）。

## 六、RBAC 三要素

```
能不能做 = f(权限码, 角色, 作用域)
权限码 107 个 / 26 类：projects.create、review.approve、platform.dashboard.view …
角色 10 个内置 + 自定义：SYS_ADMIN(10) > INST_ADMIN(20) = OW(20) > AD(30) > WS_ADMIN(40)
                        > PR_VALIDATOR(50) > PR_REVIEWER(55) > WS_MEMBER(60) > PR_ANNOTATOR(70)
每码三态：允许 / 不设置 / 拒绝（拒绝优先，显式否决）
两条硬规则：① 只能授予等级更低（数字更大）的角色；② 不能变更自己的角色
```

| 角色 | 作用域 | 权限数 | 说明 |
|---|---|---|---|
| `SYS_ADMIN` | 平台 | 10（含 `*` 通配） | 平台管理员 |
| `INST_ADMIN` | 单位 | 64 | 单位管理员 |
| `OW` / `AD` | 团队 | 75 / 75 | 所有者 / 管理员 |
| `WS_ADMIN` | 空间 | 49 | 工作区管理员 |
| `PR_VALIDATOR` | 项目 | 13 | 验收员 |
| `PR_REVIEWER` | 项目 | 12 | 质检员 |
| `WS_MEMBER` | 空间 | 26 | 空间成员 |
| `PR_ANNOTATOR` | 项目 | 13 | 标注员 |

> **数据一致性提醒**：内置手册写"104 项 / 24 类"，接口实际返回 **107 项 / 26 类**（多出 `model_provider_connection`、`cloud_drive` 等）。文档需跟版本走。
