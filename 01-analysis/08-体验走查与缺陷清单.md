# 体验走查与缺陷清单（按严重度排序）

> 走查范围：登录 → 首页 → 数据生产（项目/数据集/证书中心）→ 标注全流程 → 模型工厂 → 组织与人员 → 系统管理，共 30 个页面、12 个弹层/抽屉。
> 标记：**P0** 阻断/安全 · **P1** 严重体验 · **P2** 一致性/打磨 · **P3** 建议
> 每条给出：现象 → 证据（截图编号见 `05-assets/screens/`）→ 影响 → 修改建议

---

## P0-1 登录验证码可程序化绕过

- **现象**：拼图缺口横坐标以明文 JSON 放在 `ticket` 的 base64 载荷里，脚本无需识图即可通过。
- **证据**：`07-data/samples/login-captcha.json`；`09-技术架构与安全观察.md §2`
- **影响**：任意账号可无限次爆破；超管账号一旦被撞库，云存储 AccessKey、全平台数据面全部暴露。
- **建议**：offset 只存服务端；ticket 改不透明随机 id；同 IP+账号 5 次失败锁定。

## P0-2 SPA 直链刷新 / 新窗口打开 → 503 白屏

- **现象**：`/datasets/new`、`/projects/new`、`/projects/218/tasks/10218`、`/model-factory/scene-survey/photos` 直接访问返回 `Service Temporarily Unavailable`。
- **证据**：抓取记录 4 处 503；`05-assets/screens/` 中 `deep-datasets.png`、`extra-projects_new.png` 为全白错误页。
- **影响**：用户从 IM 里点别人分享的链接 = 白屏；**排障时无法区分"功能没做"和"服务挂了"**（手册 FAQ 第一条就是这个）。
- **建议**：路由层区分 404；SPA 加 `errorElement`；未部署功能用 feature flag 隐藏入口，别让人点到报错。

## P1-1 同名指标三种口径，无作用域标注

- **现象**：
  - 首页「标注项目 **80** 个」
  - 项目列表「项目总数 **47** 个」
  - 数据大屏「项目 **95**」
  - 项目卡片「**0/30 · 0%**」vs 同项目任务管理器「待领取 22 / 进行中 8 / 已完成 0」
- **证据**：`02-home.png`、`04-projects.png`、`03-dashboard.png`、`05-task-manager.png`
- **影响**：用户第一反应是"数据错了"，直接摧毁对平台的信任；这是**最容易被客户在会上指着问**的问题。
- **建议**：所有数字卡强制带 `scope chip`（本团队/本单位/全平台）；"已标注"与"已通过"两个词在任何地方不得混用，统一术语表。

## P1-2 任务卡在"标注中"无法自愈（高频客诉）

- **现象**：标注员点「更新」存草稿但没点「提交」，任务永久停在"标注中"（该项目 30 条任务里 7 条处于此状态，占 23%）。界面上"已领取未保存"与"已存草稿"视觉完全一致。
- **证据**：`05-task-manager.png`（进行中 8）、`06-annotate.png`（底部「提交」按钮）
- **影响**：产能黑洞。平台整体 4,157 条"进行中"、交付率仅 3.9%——这个状态设计是主因之一。
- **建议**：
  1. `annotating` 拆 `drafting` / `working` 两个子状态；
  2. 数据页对"草稿 >24h 未提交"给黄色标记 + 一键提醒；
  3. 退出标注页时若未提交，二次确认（"你有未提交的标注，离开将保留为草稿"）。

## P1-3 项目进度口径与任务状态机不一致

- **现象**：项目卡片进度用"已标注任务/任务总数"，但状态机是六态；"已标注 1 条"与"已通过 0 条"同时出现，卡片显示 0%，统计页显示 3.33%。
- **证据**：`04-projects.png`（0/30 0%）vs `09-project-stats.png`（任务进度 0% · 标注中 7 · 待审核 1 · 数据分布）
- **影响**：项目管理员无法从卡片判断"到底完成多少"。
- **建议**：进度条改为三色分段（已通过 / 在途 / 未开始），并在 hover 给出 6 态明细；`%` 只按"已通过"算，明确写"通过率"。

## P1-4 打回零成本：激励设计漏洞

- **现象**：扣分在"最终通过时按次数一次性结算"；任务若被打回后放弃，则打回不产生成本。标注员最优策略 = **先全交一遍，被打了再说**。
- **证据**：`05-数据模型与状态机.md §5`；手册 §12.1
- **影响**：质检员工作量暴涨（审核中 68 条积压），质量前置失效。
- **建议**：打回即扣（可回滚差额）；或 `reject_count≥2` 时基础分系数 ×0.5；对"零打回率"给额外奖励（现在只有"首稿加成"，权重不够）。

## P1-5 三套视觉语言并存

- **现象**：外壳＝浅蓝玻璃拟态（背景 `rgb(243,248,255)`、按钮 `#2B91F8`）；标注页＝Label Studio 沙色系（`--color-sand-200` 表头、深蓝提交按钮 `#4a5b8c`）；大屏＝深蓝（`rgb(11,32,57)`）。
- **证据**：`04-projects.png` / `06-annotate.png` / `03-dashboard.png` 三张并排即成证据。
- **影响**：用户从列表点进标注，感觉"跳到了另一个产品"；品牌一致性受损；也让前端无法复用组件。
- **建议**：外壳与标注页统一到同一 token 集（见 `03-design/01-设计系统.md`）；标注页保留 LS 画布行为，但换皮为外壳配色。

## P2-1 弹层内表单信息密度过高，且缺"为什么"

- **现象**：新建数据集弹层的"可见性"四选一（私有/团队/单位/公开）用一大段文字解释规则，用户要读 60 字才能选。
- **证据**：`14-dataset-new.png`
- **建议**：四选一改成卡片式（标题 + 一行副标题 + 图标），详细规则放 `?` 气泡；默认值高亮并写"推荐"。

## P2-2 「模型应用」是营销页却放在生产后台

- **现象**：具身智能/工业质检/校园安防/茶叶工控/海洋三文鱼 5 个方案页，是内容型落地页（大标题、KPI、能力矩阵），与后台操作无耦合，且「模型应用」分组下混着"茶叶识别管理后台"这种**实际可操作的控制台**。
- **证据**：`19-app-embodied.png`、`22-app-tea.png`
- **影响**：标注员/管理员在里面找不到出口；而真正要用的"茶叶工控控制台"被埋在营销页里。
- **建议**：拆成两个入口——「行业方案」（内容，外链官网）与「行业控制台」（工具，进后台）；后台导航只保留后者。

## P2-3 表格列宽与空状态

- **现象**：单位表格（`26-org-admin.png`）"组织层级"列把"培训机构 · 单位管理员：xxx@qq.com · 注册于 11-12 10:54"三行挤在一格，扫读困难；多处空状态是"暂无数据"四字，无引导。
- **建议**：一行一信息（层级用 chip、邮箱单独列）；空状态统一为"图标 + 一句解释 + 一个主行动"（平台在项目列表的空态做对了，可推广）。

## P2-4 深色大屏与浅色外壳切换无过渡，且时间/日期格式不统一

- **现象**：大屏内 `2026/11/14 15:45:53`，项目列表 `2026-11-14 13:50`，流水 `2026/11/14 11:13:49`，证书 `2026-11-11 03:42`。
- **建议**：全局时间组件统一 `YYYY-MM-DD HH:mm`，相对时间（"3 小时前"）用于列表，绝对时间用于详情与导出。

## P2-5 文档与实现漂移

- **现象**：内置手册写"权限码 104 项 / 24 类"，接口实际 **107 / 26**；手册写"模型超市 128 个模型"，实际在架 **21** 个；手册写"数据集分类 5 大类 26 子类"，接口返回 **47 节点**（含行业分类层）。
- **证据**：`06-接口清单与数据字典.md`、手册原文对照
- **影响**：客户拿手册验收会对不上；对外交付物出现不可核对的数字是信任问题。
- **建议**：手册改为**从代码生成**（权限码、分类树、格式清单都能自动导出），或至少标注"截至 vX.Y"。

## P3-1 服务器路径暴露在 UI 数据里

- 训练集"来源"列显示 `本机目录`，但接口里带 `/root/projects/.../data.yaml`；模型详情暴露 `/opt/label-studio-data/marketplace/...best.pt`。
- **建议**：前端展示"本机目录"，接口不返回绝对路径。

## P3-2 无移动端适配

- 标注画布在移动端不可用（这符合行业现实），但**审核/验收**完全可以在手机上做（看缩略图 + 通过/打回）。当前无响应式布局，浪费了一个高频轻操作场景。

## P3-3 卡片信息重复

- 项目卡片同时给"0/30 0%"+"六态计数"，信息重复度高，卡片高度 200px+，一屏只能看 8 个。**建议**：默认紧凑卡（名称+进度+2 个关键数），hover/展开才显示六态。

## 走查评分（10 分制，产品经理视角）

| 维度 | 分数 | 理由 |
|---|---|---|
| 信息架构 | 8.5 | 导航与角色同构、项目页签即流程，非常清晰 |
| 流程设计 | 8.0 | 三级流转 + 发布四检查 + 撤回不删数据，专业级 |
| 视觉一致性 | 5.5 | 三套视觉语言并存，token 未统一 |
| 文案质量 | 8.5 | "为什么模型是灰的"这类解释性文案是全站亮点 |
| 数据可信度 | 5.0 | 同名三口径 + 文档漂移，最伤信任 |
| 安全 | 3.0 | 验证码可绕、无 MFA、路径与 AK 暴露 |
| 性能 | 7.0 | 首屏快，但大响应 + 4.3MB bundle |
| 可维护性 | 6.5 | 模块命名清晰，但双前端耦合、label_config 无版本 |
| **综合** | **6.6** | 骨架专业、细节欠打磨；先修信任与安全，再谈功能 |

## 三步修复路线（建议排期）

1. **第 1 周**：P0-1 验证码、P0-2 错误码拆分、P3-1 路径脱敏（都在后端，1 人 3 天）
2. **第 2-3 周**：P1-1 口径统一（抽 `StatCard` + `scope`）、P1-3 进度分段、P1-2 草稿子状态（前端 + 1 个接口字段）
3. **第 4-6 周**：P1-4 积分规则调整（产品 + 财务对齐）、P1-5 视觉收敛（设计系统落地）
