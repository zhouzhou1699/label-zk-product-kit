# 技术架构与安全观察

> 视角：产品经理做技术尽调——只关心"哪些技术事实会变成产品约束或商业风险"。

## 一、架构还原

```
                        ┌──────────────── nginx (443) ────────────────┐
                        │  /                    → Django 模板 + React SPA
                        │  /user/login/         → Django 模板（品牌化登录页）
                        │  /static/branding/*   → 自研 CSS/JS（puzzle.js 等）
                        │  /react-app/main-*.js → 业务 SPA（4.4 MB 单 bundle）
                        │  /api/*               → Django REST（LS + 自研扩展）
                        │  /storage-data/*      → 文件服务（?filepath=&thumb=）
                        └───────────────────┬──────────────────────────┘
                                            │
              ┌─────────────────────────────┼──────────────────────────────┐
              ▼                             ▼                              ▼
     Label Studio OS 1.24.0.dev0     自研扩展 app                   外部依赖
     ├ label_config 引擎              ├ 组织/RBAC/institutions        ├ 阿里云 OSS
     ├ Data Manager (DM2)             ├ workflow（三级流转）           ├ AMD ROCm 训练集群
     ├ /api/tasks /api/dm             ├ rewards（积分/证书 PDF）       └ S3 兼容（头像）
     └ /api/ml /api/templates         ├ model-factory（超市/训练）
                                      └ branding（登录页拼图）
```

**关键判断：这是"外挂式"架构，不是"重写式"。**

- 业务 SPA 与 LS 前端是**两套独立应用**：`/projects/218/data` 页面在同一个 URL 里切换成 LS 风格的标注器（左侧任务列 + 画布 + 右侧面板），DOM 结构与 `/projects` 完全不同 —— 证据是标注页的标签条、`shift+1` 适应窗口、`Ctrl+滚轮` 缩放都是 LS 原生行为。
- 后果 1（好）：LS 升级能拿到上游能力；后果 2（坏）：**样式与交互无法统一**，标注页的深蓝按钮、圆角、字体都和外壳不一致（见 `05-assets/screens/06-annotate.png` vs `04-projects.png`）。
- 后果 3（坏）：任何 LS 侧崩溃 = 标注页整页白屏，而外壳只会显示一个 `Service Temporarily Unavailable`。

## 二、登录安全（实测，P0 缺陷）

### 2.1 拼图验证码的挑战结构

```http
POST /api/branding/login/captcha
→ {"ticket":"eyJvZmZzZXQiOjIyMiwicHVycG9zZSI6ImxvZ2luIiwicGljdHVyZSI6InNsaWRlLTA5Iiwic2VlZCI6IjYyMzkwMzE2YmNiMmQzZGUiLCJub25jZSI6IjFiMTQ5ZWFmZWExOGI2M2YifQ:1xS8Nr:GX2JsprA3fqQJ9v4MKmvBW1FCjvoTEd30F__x5Cuvn0",
   "background":"data:image/jpeg;base64,…",
   "piece":"data:image/webp;base64,…",
   "track":{"width":320,"height":104},
   "piece_box":{"width":46,"height":46,"top":29.0},
   "tolerance":10}
```

`ticket` 由三段组成：`base64(payload) : timestamp : signature`。对第一段做 base64 解码：

```json
{"offset":222,"purpose":"login","picture":"slide-09","seed":"62390316bcb2d3de","nonce":"1b149eafea18b63f"}
```

**`offset`（缺口真实横向坐标）以明文放在客户端可读的 payload 里**——base64 是编码不是加密。前端 `puzzle.js` 的注释甚至明说"the offset never leaves the server"，但实际上它随 ticket 一起下发给了浏览器。

### 2.2 后果

```python
# 实测：无需看图，直接解码 ticket 得到 offset，提交即通过
payload = json.loads(b64url(ticket.split(':')[0]))
verify(ticket, position=payload['offset'])   # → {"ok": true, "token": "…"}
```

- 攻击者可用脚本对任意账号做**无限次密码尝试**（每次先取挑战 → 解 offset → 过验证 → 试密码），验证码的保护作用为零。
- 未观察到 IP 级限流或账号锁定提示。
- 会话有效期 14 天（`Max-Age=1209600`），且 `HttpOnly`（这点是对的），但无设备管理、无异地登录提醒、无 MFA。

### 2.3 根因与修复

| 层 | 问题 | 最小修复 |
|---|---|---|
| 设计 | 把判定答案放在客户端可读的签名载荷里 | offset 只存服务端（Redis/DB，key=ticket id）；ticket 改不透明随机串 |
| 实现 | `tolerance:10` 也在响应里 | 容差服务端常量，不下发 |
| 运营 | 无失败计数、无锁定 | 同 IP+账号 5 次失败锁 15 分钟；超管账号强制 MFA |

> 说明：这是"把事情做快了"的典型症状——拼图 UI 做得很精致（canvas 粒子背景、aurora 光晕、拖拽手感），但判定逻辑省了最关键的服务器侧状态。

## 三、其它安全问题（按优先级）

| # | 问题 | 证据 | 风险 | 修复 |
|---|---|---|---|---|
| 1 | 验证码答案泄露 | 上述 | **高**：撞库/爆破 | 服务端存 offset |
| 2 | 管理员无 MFA | 登录仅 email+password | **高**：超管可看全平台数据、可配 OSS AccessKey | TOTP / 短信 |
| 3 | 服务器绝对路径泄露 | 训练集字段 `dataset_key:"/root/projects/knife_stick_ft/merged/data.yaml"`；模型 `weights_path:"/opt/label-studio-data/marketplace/model_0015/best.pt"` | 中：暴露部署结构，便于后续攻击 | 路径只存相对 ID，前端不返回 |
| 4 | OSS AccessKey 出现在头像 URL 查询串 | `?AWSAccessKeyId=LTAI5t9ihRdKJGUAGeEsUZ99&Signature=…&Expires=…` | 中：AK 长期暴露（预签名 URL 本不该带 AK ID） | 用 STS 临时凭证或 CDN 域名 |
| 5 | 大响应无分页（154 KB / 156 KB） | `/api/templates`、`training/overview` | 低：可用性 | 分页 + 字段投影 |
| 6 | 无 CSRF 以外的越权测试结论 | `my_permissions` 由服务端下发，`actions[]` 服务端算 | 低（设计正确） | 建议做一次 IDOR 扫描（`/api/projects/{id}` 换 id） |
| 7 | 错误码混用（503 表一切） | 路由不存在也 503 | 低：掩盖真实故障 | 区分 404/500 |

## 五、可维护性观察（决定后续交付速度）

1. **`label_config` 是唯一的"能力声明"**：它同时决定界面、可用模型、可导出格式。好处是"改一处全通"，坏处是**没有版本化**——改配置后历史标注可能失效（手册承认，只能"重置缓存"兜底）。**建议**：`label_config` 加版本号与迁移检查（对比新旧 tag 集合，冲突时禁止保存并给出受影响的标注数）。
2. **`include=` 字段投影已存在**（项目列表用了），说明团队知道按需返回，但只在少数接口推行——这是"局部好实践没有制度化"。
3. **自研模块命名清晰**（`workflow/`、`rewards/`、`model-factory/`、`branding/`），API 前缀可读性高，比"一个大 app 全塞"强很多。
4. **前端无设计系统复用**：外壳用浅蓝玻璃拟态（`rgb(243,248,255)` 背景 + 蓝渐变），标注页用 LS 的沙色系（`--color-sand-*`），大屏用深蓝（`rgb(11,32,57)`）。**三套视觉语言**，用户每次切换都在"换一个产品"。

## 六、规模与容量（决定运营策略）

| 指标 | 数值 | 洞察 |
|---|---|---|
| 单位 8 / 团队 24 / 空间 269 | 空间:团队 ≈ 11:1 | 空间粒度被用得很细（每个成员可能一个空间），可能过度拆分 |
| 项目 95 / 任务 4,825 | 项目:任务 ≈ 1:51 | 平均项目只有 51 条任务，**小项目为主**，说明是"多点验证"阶段而非"大批量生产" |
| 标注 1,148 / 任务 4,825 | 标注覆盖率 23.8% | 大量任务未标，产能是瓶颈 |
| 交付率 3.9%（172/4,413） | 极低 | 要么刚上线、要么流程卡在审核环节（审核中 68 / 打回 9 / 进行中 4,157） |
| 成员 198，今日 +105 | 单日涌入过半 | 院校批量导入的痕迹，符合"实训"场景 |

**结论**：平台处于"客户已进来、数据在灌、产能未起来"的阶段。**当前最紧要的产品问题不是加功能，而是把 4,157 条"进行中"推过审核关**——这解释了为什么手册里 FAQ 第一条就是"任务长期卡在标注中"。

## 七、给研发的三条工程建议

1. **把 503 换成有语义的错误**：`404 route_not_found` / `502 upstream_label_studio` / `503 feature_not_deployed`，前端按 code 渲染不同引导。当前"什么都不通 = 503"会让每次故障排查都从零开始。
2. **抽出 `StatCard` 组件并强制带 `scope`**：解决三处口径不一致（80/47/95），同时统一卡片视觉。
3. **标注页做"壳内嵌"而不是"路由内切换"**：给 LS 前端套一层统一的顶部面包屑与提交栏（保留 LS 画布），把三套视觉语言收敛成两套（外壳浅色 + 大屏深色），标注页跟随外壳配色。
