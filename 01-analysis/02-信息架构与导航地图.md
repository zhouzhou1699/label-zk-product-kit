**架构判断**
- 侧栏固定分组、顺序不可自定义（手册明确写出）——牺牲灵活性换稳定性，对"每月只用两次的管理员"是对的，对每天用的标注员是负担（标注员需要的其实只有"项目 → 任务"两跳）。
- **角色同构**：导航分组 ≈ 角色分工。标注员只关心"数据生产"，管理员只关心"组织与人员/系统管理"。这是它能不写说明书就被用起来的原因。
- 深度问题：最深的操作路径是 **4 跳**（组织管理 → 个性化设置 → 云存储 → 保存），超出 3 跳的规则，容易迷路。

## 三、项目内页签（纵向流程与导航同构）

项目的七个页签不是并列功能，而是**一条流水线的七个截面**：

```
角色设置 → 设置 → 奖励 → 项目发布 ─┬─ 数据统计
  (谁干)   (怎么干) (干完给什么)      ├─ 数据导出
                                    └─ 任务管理器（干活的地方）
```

页签上数字 `1 2 3 4` 是**步骤序号**，且"发布"之后才解锁"任务管理器"的可领取任务——导航本身在讲流程。这是我在这个产品里最认可的 IA 决策。

## 四、页签式统计的口径问题（IA 层缺陷）

同一"项目数"在三处三个值，且界面均未标注作用域：

| 位置 | 数值 | 实际作用域（推断） |
|---|---|---|
| 首页 · 平台概览 | 标注项目 **80** | 本单位（光线科技）全部团队 |
| 项目列表 · 项目总数 | **47** | 当前团队（刘成龙的团队） |
| 数据大屏 · 项目 | **95** | 全平台 |

**改法（最小改动）**：所有数字卡统一加一行 `scope chip`（`本单位` / `本团队` / `全平台`），把"信任"补回来。这是 1 个组件的事，不是架构的事。
