> 拆解对象：`https://label-dev.zhongkaisk.cn/`（开发/演示环境，2026-11-14 抓取）

## 一、一句话结论

**这不是一个"标注工具"，而是一个「数据资产工厂」的操作系统**：以单位（Institution）为数据边界、以团队（Organization）为协作边界、以空间（Workspace）为项目容器，把"原始数据 → 标注 → 一审 → 终审 → 数据集沉淀 → 训练 → 模型 → 预标注"做成一条**有状态、有归属、可追溯、可结算**的闭环流水线。

技术上它是 **Label Studio OS 1.24.0.dev0（Community 版）的深度二次开发**——保留了 LS 的 `label_config` 标注引擎与数据管理器（DM），在外围自研了四层东西：组织与 RBAC、项目三级流转工作流、标注奖励（积分+证书）、模型工厂（超市/训练/行业应用）。这一点决定了它的能力天花板与所有体验缺陷的来源，后文所有判断都建立在这个事实上。

---

## 二、它到底解决什么问题

标注行业最常见的失败不是"标得慢"，而是**标完之后说不清来路**：这批图谁标的、谁审的、改过几版、能不能直接训练、下一个项目还能不能复用。

平台把这件事拆成三个可交付的承诺（登录页三张卡即为产品定位，见 `05-assets/screens/01-login.png`）：

| 承诺 | 对应机制 | 真实落点 |
|---|---|---|
| **边界清晰（ISOLATION）** | 单位 → 团队 → 空间 → 项目 四层隔离 + 权限码/角色/作用域三重判定 | 单位间数据互不可见；数据集可"分发"给下级而不复制 |
| **流程可视（WORKFLOW）** | 待领取 → 标注中 → 待审核 → 待验收 → 已通过（+ 已打回）六状态机 | 项目卡片直接摊开六个计数，卡在哪一环一眼可见 |
| **结果可复用（REUSE）** | 标注成果 → 数据集 → 训练集 → 模型 → 预标注 | 训练完成自动进"私有货架"，回到项目里当预标注模型 |

## 三、用户与角色（谁在用，用什么换什么）

平台把使用者切成三层，这不是抽象模型，而是**界面与权限的真实分界线**：

| 角色 | 视角 | 关键页面 | 他真正的 KPI |
|---|---|---|---|
| **平台管理员（超管）** | 跨单位 | 数据大屏、超管设置（登录页品牌/企业空间/问题反馈）、RBAC 角色模板 | 平台运营指标、配额不爆、品牌一致 |
| **单位管理员** | 本单位 | 组织管理（单位/团队/个性化/云存储/模型配置）、申请审批 | 人进得来、数据不丢、存储不超、模型可接 |
| **项目管理员** | 单个项目 | 角色设置、项目设置、发布、数据统计、导出 | 项目按期交付、质量达标 |
| **标注员** | 任务 | 任务管理器、标注工作台 | 通过率高、积分多、别被打回 |
| **质检员 / 验收员** | 一批任务 | 验收页签、验收台账 | 漏检率、一致性 |

**拆解判断**：这套角色设计最聪明的一处是把「审核」和「验收」拆成两个节点，并且**只有终审通过才结算积分**——把"质量"直接接到了"钱"上。这是它区别于开源 Label Studio 的核心产品化设计。

## 五、核心业务闭环（这是它的产品内核）

```
      ┌──────────── 数据集 / 上传 / 云存储 / 内置数据集 ───────────┐
      │                                                          │
      ▼                                                          │
   建项目（生产模式 / 院校实训模式）                                 │
      │                                                          │
      ▼                                                          │
  导入数据 → 生成任务 → 发布（四项前置检查）                          │
      │                                                          │
      ▼                                                          │
  标注（工作台，label_config 驱动）→ 提交                            │
      │                                                          │
      ▼                                                          │
  一审（质检员：通过 / 打回，打回计数）                                │
      │                                                          │
      ▼                                                          │
  终审（验收员：评分 0–100 + 结论）★ 唯一结算点                       │
      │                                                          │
      ├── 通过 → 积分结算 + 证书评估 → 验收台账                        │
      │                                                          │
      ▼                                                          │
  导出（JSON/CSV/COCO/云存储直传）→ 生成训练集 → 模型训练 → 模型超市私有货架
      │                                                          │
      └───────────── 预标注 / 预测 ────────────────────────────────┘
```

**闭环是否真的闭上？** 数据上闭了（数据集可引用、模型可回灌），但**产品上差最后一跳**：模型部署回项目后，缺少"预标注采纳率 / 模型对产能提升"的度量——你在平台里看不到"用了这个模型，人省了多少"。这是我认为最值得补的一块。

## 七、技术事实（决定了它的能力边界）

| 维度 | 事实 | 来源 |
|---|---|---|
| 后端 | Label Studio OS `1.24.0.dev0`，edition **Community**，backend commit `5204dc5+dirty`，branch `dev` | `GET /api/version` |
| 前端 | Django 模板（登录/鉴权页）+ React SPA（业务台，bundle 4.4 MB `main-KA5OhVdG.js`）+ Label Studio 标注前端（iframe 外挂） | 页面源码 |
| 鉴权 | Django session cookie + CSRF Token；会话 14 天；登录带**滑块拼图验证码** | 抓包 |
| 部署 | nginx + 阿里云 OSS（头像/存储），`/opt/label-studio-data` 为数据根 | 响应头、权重路径 |
| 训练集群 | `YANXI-YTJ-AMD-M1`，8 × **Radeon Pro W7900**（AMD ROCm 路线，非 NVIDIA） | `/api/model-factory/training/overview/` |
| 规模 | 8 单位 / 24 团队 / 269 空间 / 95 项目 / 4,825 任务 / 198 成员 | `/api/dashboard/overview` |

**这意味着什么**：它拿到的是 LS 的"标注能力"（25 种标注范式、`label_config` XML 驱动、DM 视图），但 LS Community 版**本身没有**多租户、没有三级流转、没有积分证书、没有模型市场。这些全是这家公司自己在外围搭的。所以：

- 优点：标注引擎成熟，能覆盖图像/文本/语音/视频/对话五大类 26 子类；
- 风险：**双前端架构割裂**（React 外壳 + LS iframe 内核），标注页一旦 503 就是白屏；升级 LS 版本会同时牵动三处；
- 风险：`label_config` XML 直接暴露给项目管理员编辑，改配置即可能让历史标注失效（手册也承认，只能靠"重置缓存"兜底）。

## 八、产品化亮点（值得抄的 7 处）

1. **发布前四项检查**（标签配置 / 数据已导入 / 任务已生成 / 成员已加入）——把"发不出去"的失败前置成清单，每项带「查看」跳转。这是把运维经验产品化的典范。
2. **项目卡片即仪表盘**：六个状态计数直接摊在卡片上，不点进去就知道积压在哪。
3. **撤回发布不删数据**：只暂停新任务领取，已有标注完整保留。降低"发错了"的心理成本。
4. **积分公式把质量接进钱**：`max(0, 基础分 + 评分加成 + 首稿加成 − 打回扣分×次数)`，且只在终审通过时结算一次——避免"刷量刷积分"。
5. **证书中心用真实 PDF 渲染预览**（A4 横向 297×210mm，layout 元素化，预设底纹 navy-gold），所见即所得，不是假缩略图。
6. **模型准入四道关卡**（提交文档 → 基准评测复现 → 安全合规审计 → 灰度 7 天），并把"未通过原因"写在卡片上——用产品语言表达风控。
7. **"为什么模型是灰的"**：模型与控件能力不匹配时，灰显卡片直接写原因（"这个项目没有矩形框控件"），而不是静默禁用。**这是全站最好的一处微文案。**

## 九、产品化短板（必须改的 8 处）

> 细节与截图见 `01-analysis/08-体验走查与缺陷清单.md`，此处只给结论。

1. **登录验证码可被程序化绕过**：滑块偏移量以明文 JSON 放在签名 ticket 里（base64 仅编码不加密），实测无需看图即可 100% 通过。这是安全级缺陷，不是体验问题。
2. **同名指标三种口径**：首页"标注项目 80 个"、项目页"47 个"、大屏"95 个"，界面未标注作用域，用户会认为是数据错误。
3. **SPA 直链刷新即 503**：`/datasets/new`、`/projects/new`、`/projects/218/tasks/10218` 直接访问返回 503。手册承认这是"接口统一 503"策略，但把**路由不存在**和**后端异常**混成同一个错误码，排障成本极高。
4. **项目进度口径自相矛盾**：项目卡片显示"0 / 30 · 0%"，同项目的任务管理器显示"待领取 22 / 进行中 8 / 待处理 0 / 已完成 0"。已完成和已标注不是一回事，但界面没说清。
5. **文档与实现漂移**：手册写"权限码 104 项 / 24 类"，接口实际 107 项 / 26 类；手册写"模型超市 128 个模型"，实际在架 21 个。**对外手册出现无法核对的数字，是交付信任问题。**
6. **激励漏洞**：打回扣分在"最终通过时一次性结算"，若任务被打回后再没通过，则打回零成本 → 标注员倾向于"先交再改"。
7. **服务器路径泄露**：训练集来源字段直接把 `/root/projects/knife_stick_ft/merged/data.yaml` 打到前端。
8. **无 MFA、无登录失败锁定提示、会话 14 天不可视**：管理员账号（可看全平台数据 + 可配云存储 AccessKey）只有单密码保护。

## 十、商业与定位推断

- **客户画像**：制造/质检（玻璃瓶缺陷、刀具、货架）、院校实训（山东外国语大学、张家口职业技术学院）、农业（茶叶、三文鱼）——这是"AI 落地服务商 + 数据标注产能"的混合生意，不是纯 SaaS。
- **商业模式推断**：项目制交付（数据标注 + 模型训练 + 边缘部署）为主，平台是**交付基础设施 + 客户自服务入口**；院校版是获客与产能池（学生即标注人力，实训模式不计积分正是这个逻辑）。
- **真正的壁垒**：不是标注界面（开源可替代），而是**组织/权限/结算/证书这一层"可审计的产能管理"**，以及已经跑通的行业模板（工业质检/校园安防/茶叶工控）。

## 十一、如果让我接手，三件事按顺序做

| 优先级 | 动作 | 理由 | 预期 |
|---|---|---|---|
| P0 | 修验证码（服务端保存 offset，ticket 改不透明随机串）+ 管理员 MFA | 现有实现等于没有验证码 | 登录攻击面归零 |
| P1 | 统一指标口径：所有数字加作用域标签（本单位/本团队/全平台），并抽一个 `StatCard` 组件强制带 `scope` 属性 | 现在三个页面对同一名词给三个数，直接摧毁信任 | 客诉类工单下降 |
| P2 | 把"模型 → 产能"度量补上：预标注采纳率、人工修正耗时、单位任务成本 | 闭环缺最后一跳，卖模型时没有证据链 | 模型工厂从"货架"变成"ROI 证明" |
