## 二、三种使用场景

### 场景 A：向老板/客户汇报（10 分钟）
1. 打开 [`README.md`](../README.md) 的「核心结论（5 条）」
2. 展示 [`05-assets/annotated/A01-项目列表.png`](../05-assets/annotated/A01-项目列表.png)（口径问题最直观）
3. 展示 [`05-assets/annotated/A02-任务管理器.png`](../05-assets/annotated/A02-任务管理器.png)（产能卡点）
4. 打开原型 → 切到「产能看板」（回答"如果重构，会长什么样"）
5. 收尾用 `01-analysis/01-产品拆解报告.md` 的「如果让我接手，三件事按顺序做」

### 场景 B：立项评审（产品 + 研发 + 测试）
1. 宣讲 [`02-prd/01-产品需求文档-PRD.md`](../02-prd/01-产品需求文档-PRD.md) 的 §0 一页纸摘要 + §3 Epic 总览
2. 逐 Epic 过 §4 功能需求（每条都有验收标准，测试可直接提用例）
3. 用 [`02-prd/02-用户故事与验收标准.md`](../02-prd/02-用户故事与验收标准.md) 的 Gherkin 做验收基线
4. 用 [`02-prd/03-术语表与指标字典.md`](../02-prd/03-术语表与指标字典.md) 统一全团队口径（这条最容易被跳过，但它是所有口径问题的解药）

### 场景 C：UI/前端开工
1. 先读 [`03-design/01-设计系统.md`](../03-design/01-设计系统.md)，把 `tokens.css` 接进项目
2. 按 [`03-design/02-页面规格说明.md`](../03-design/02-页面规格说明.md) 逐页实现
3. 对照 `05-assets/prototype/*.png` 做视觉验收
4. 对照 `05-assets/screens/*.png` 确认"原来长这样、要改成这样"

## 四、三条最容易踩的坑（给接手团队）

1. **不要先动视觉。** 三套视觉语言（浅蓝外壳 / LS 沙色标注页 / 深色大屏）确实难看，但先改视觉会掩盖真问题：数据不可信。先统一口径与术语，再统一视觉。
2. **不要重写标注画布。** Label Studio 的画布（快捷键、撤销、区域/关系面板）是它最强的部分。重构只做"壳层"：顶栏、按钮、配色、打回历史页签。重写画布 = 6 个月 + 一定退化。
3. **不要给 `label_config` 加复杂抽象。** 它是整个平台的能力中枢（界面+模型+导出格式全由它决定），但现在已经没有版本控制。**加"变更影响预检"比加抽象层重要 10 倍**：保存前对比新旧标签集，冲突时禁止并给出受影响标注数。

## 五、没做的事（明确边界）

| 未做 | 原因 |
|---|---|
| 移动端设计 | 标注画布需要精确输入；但审核/验收可移动化，单独立项 |
| 完整 UI 稿（Figma） | 交付物是 HTML 原型 + token + 页面规格，Figma 可由 UI 按规格 1:1 还原 |
| 后端实现代码 | 本包是产品交付物，不含研发实现 |
| 真实客户数据 | 全部来自测试环境，人名/邮箱/路径已脱敏 |
| 竞品的定量基准 | 无公开数据，只做能力矩阵定性对比 |

## 七、如果要继续推进

建议接下来做三件事（按顺序）：

1. **做一次 60 分钟的口径对齐会**（产品 + 研发 + 数据）：把术语表过一遍，确定 4 个 scope 的定义，把"已标注/已通过"彻底分开。这件事不写代码，但能消掉 30% 的客诉。
2. **拿一个真实项目跑产能看板的线下原型**（Excel 也算）：用近 30 天数据算漏斗停留时长，验证"瓶颈在审核"这个结论是否成立，再决定是否开发。
3. **给验证码做一次渗透复测**：用 `06-接口清单` 里的两个端点写脚本，确认修复后无法在不解图的情况下通过。
